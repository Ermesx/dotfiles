# ADR-0001: Install Windows software declaratively through DSC v3

- **Status:** Accepted
- **Date:** 2025-09-01 (implemented in `32f284b`; recorded 2026-10-15)
- **Decider:** repository owner

## Context

The repo sets up a Windows developer machine from one chezmoi source. Software installation went through two
earlier approaches before this decision:

1. **Imperative PowerShell** (`Dotfiles-Toolkit`: `Install-OrUpdateApp`, `Install-OrUpdateModule`). Every package
   needed hand-written "is it installed / install / update" logic, and the scripts were a second codebase to test
   and maintain.
2. **`winget configure` with `*.dsc.winget` files** (`6db5d52`, 2025-08-26). Declarative, but the package list lived
   in three hand-maintained YAML files (`packages`, `modules`, `windows`), duplicated what tests and the profile
   needed, and ran on the PowerShell DSC (v2) engine behind winget.

Forces:

- One list of packages should drive installation, tests, the PowerShell profile, and documentation.
- Re-running setup must be safe (idempotent) and cheap to check for drift without installing anything.
- Three package kinds must be covered: winget apps, PowerShell modules, .NET global tools — plus a few OS
  settings (Developer Mode, Explorer, clock).
- The source is shared with Linux, so the Windows mechanism must fit chezmoi templating rather than replace it.

## Decision

All Windows software that has a DSC resource is installed through **Microsoft DSC v3** (`dsc config set`), from a
document generated by chezmoi:

- `home/.chezmoidata/packages.yaml` is the single source of truth.
- `home/.chezmoitemplates/config.dsc.yaml.tmpl` renders it into one DSC v3 configuration document using
  `Microsoft.WinGet/Package`, `PowerShellModule/PSModuleResource`, `Microsoft.DotNet.Dsc/DotNetToolPackage`, and the
  `Microsoft.Windows.Settings` / `Microsoft.Windows.Developer` resources for OS settings.
- `run_onchange_before_01-dsc.ps1.tmpl` embeds the rendered document, so chezmoi reruns it only when the package
  list or the template changes. The result is written to `%TEMP%\config.dsc.result_<timestamp>.yaml`.
- Adding software means adding a line to `packages.yaml`. No per-package install scripts.

### Explicit exceptions

DSC is not used where there is no suitable resource or where it is needed before DSC exists:

| What | How | Why not DSC |
|---|---|---|
| winget, chezmoi, `Microsoft.DSC`, PowerShell 7 | `install.ps1` | Bootstrap: the engine cannot install itself |
| DSC resource modules | `run_once_before_00-pre-dsc.ps1` (`Install-Module`) | Must exist before `dsc config set` runs |
| WSL distro | `run_once_before_install-wsl.ps1.tmpl` | No adopted DSC resource |
| Nerd Font | `run_once_before-install-font.ps1.tmpl` | Downloaded from GitHub releases, not a package |
| yazi plugins | `run_once_after-yazi-plugins.ps1.tmpl` | No DSC resource; needs yazi installed first |

New exceptions are allowed only on the same grounds and must keep reading their list from `packages.yaml`.

## Alternatives considered

| Option | Why rejected |
|---|---|
| Keep imperative scripts | Idempotency and update logic written by hand per package kind; no drift check |
| Keep `winget configure` + `*.dsc.winget` | Static files outside chezmoi data, list duplicated across consumers, older PowerShell DSC engine |
| `winget import` (JSON) | Covers winget apps only — not modules, .NET tools, or OS settings |
| Scoop / Chocolatey | Another package source and trust boundary; no settings management; winget already covers the catalog |
| Ansible / other CM tools | Needs a control node or extra runtime; too heavy for a single-user workstation |

## Consequences

Positive:

- One declarative list; templates, profile imports, and tests derive from it.
- Idempotent re-runs; `dsc config test` on the rendered document reports drift without installing anything.
- Apps, modules, .NET tools, and OS settings go through one engine and one result file.
- Microsoft's supported direction for Windows configuration (WinGet and Windows resources target DSC v3).

Negative / costs:

- **Install-only.** Removing an entry from `packages.yaml` does not uninstall it (no `_exist: false` /
  `Ensure: Absent` is generated). Cleanup is manual.
- **Converges only on change.** `run_onchange` reruns DSC only when the rendered document changes; manual drift on
  the machine is not corrected until the list changes or the script is forced.
- **No version pinning.** Every package resolves to the latest version from its source; a fresh install is not
  reproducible over time.
- **Prerelease dependencies.** `Microsoft.DotNet.Dsc`, `Microsoft.Windows.Settings`, and
  `Microsoft.Windows.Developer` are installed with `-AllowPrerelease`; `PSModuleResource` comes from the community
  `PowerShellModule` module. Breaking changes in these resources break setup.
- Requires admin rights and PowerShell 7 for the run

## When to revisit

- DSC v3 or a resource used here is deprecated, or a prerelease resource stays broken for a release cycle.
- Uninstall or version pinning becomes a real requirement (e.g. a second machine that must match exactly).
- A cross-platform mechanism (Linux) is chosen that could also drive Windows from the same list.
